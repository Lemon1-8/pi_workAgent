# 电商团队 Work Agent 需求与技术调研

更新日期：2026 年 10 月 13 日。阶段：需求调研，实施范围与验收标准待确定。

应用面向约 50 人的电商团队，通过公司内部网页使用。XLSX 处理是必须覆盖的核心能力，涉及约 200 个店铺，单次上千份文件，每份约 5MB，以及订单合并、ERP 与平台账单对账、销售和库存分析。输出采用统一结果表。建议由 Pi 理解任务与调度工具，由批处理工具完成数据处理，再交付可预览、可下载、可追溯的结果。

## 已确认的产品条件

| 条件 | 当前信息 |
| --- | --- |
| 使用者 | 约 50 人的电商公司团队 |
| 使用入口 | 公司内部网页 |
| Agent 底座 | 用户希望基于 PI SDK；技术调研以 Mario Zechner 的 Pi 为候选 |
| 必需文件能力 | XLSX 处理 |
| 业务范围 | 多店铺订单合并、ERP 与平台账单对账、销售及库存分析 |
| 店铺和文件规模 | 约 200 个店铺，单次上千份文件，每份约 5MB |
| 数据来源 | 国内电商平台及 Temu；ERP 包括旺店通、金蝶 |
| 模板情况 | 各来源导出模板有差异，同一类数据的字段名称和工作表结构基本一致 |
| 输出要求 | 生成统一结果表即可 |
| 时间信息 | 现有 Python 程序处理一批约 40 分钟，作为后续对比基准 |
| 第一条验收流程 | 多店铺订单合并 |
| 文件入口 | 网页选择文件夹批量上传 |
| 当前部署条件 | 暂无服务器，开发验证先在本机进行 |
| 现有程序 | Python 脚本，目前不在本机；具体入口与规则待取得脚本后检查 |

50 名使用者不能直接换算为 50 个并发任务。容量目标取决于峰值提交量、每批文件数、行数、文件大小和处理复杂度。

按 1,000 份 × 5MB 粗估，单批输入约 5GB；文件解压与解析后的数据量需实测。并发应按批次与文件解析分别限额，结合实际硬件和峰值任务量确定。

## Pi SDK 的接入与边界

旧 `badlogic/pi-mono` 仓库已跳转到 [earendil-works/pi](https://github.com/earendil-works/pi)。本次查询 npm registry，`@earendil-works/pi-coding-agent` 最新发布版本为 1.2.0，要求 Node.js 至少 22.19.0。实现时应固定发布版本，并对照同版本文档。[已发布包元数据](https://registry.npmjs.org/@earendil-works%2Fpi-coding-agent/latest)

[`createAgentSession()`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/sdk.md) 可在 Node.js 或 Bun 中嵌入 Pi，提供会话存储、模型配置、工具及资源加载、流式事件和运行控制。建议先评估这一入口；只有需要全面接管上下文与资源生命周期时，再采用更底层的 `pi-agent-core`。

Pi 提供工具注册与执行调度；具体 XLSX 工具、成员身份、任务归属、批处理状态和产物管理由应用实现。Pi 默认继承启动进程的权限，没有内置文件、进程、网络和凭据限制；`cwd` 用于工作区选择，不能作为隔离机制。[官方权限说明](https://github.com/earendil-works/pi/blob/v1.2.0/README.md#permissions--containerization)

当前 1.x 仓库的包目录不含旧 `pi-web-ui`。旧 `@mariozechner/pi-web-ui` 0.73.1 的资料可作历史参考，前端选型需要避免与当前运行时混用。[当前包目录](https://github.com/earendil-works/pi/tree/main/packages)、[旧 Web UI](https://github.com/earendil-works/pi/blob/v0.73.1/packages/web-ui/README.md)

## 待确认的最小架构方案

员工网页提交任务和文件，Pi 澄清业务规则并发起批处理。任务执行器按文件解析、规范化、合并、匹配和计算；任务状态与产物单独保存，网页通过进度与异常明细呈现结果。

按平台或 ERP、数据类型与模板版本维护字段映射。同类文件复用已确认的解析规则；未知结构先展示差异，由 Agent 辅助提出映射，再确认如何处理。店铺、币种、时区、数据期间和业务粒度应随输入记录，具体必需字段由首条业务流程确定。

| 部分 | 建议职责 |
| --- | --- |
| 网页 | 文件上传与预览、任务对话、排队和进度、结果与异常下载 |
| Pi 会话 | 理解意图、澄清口径、调用有明确输入输出的工具、解释处理结果 |
| 批处理任务 | 逐文件处理、保存进度、失败文件重试、取消和恢复策略 |
| 数据与文件 | 原始输入版本、规范化记录、来源位置、生成的 XLSX 和异常明细 |

向模型提供字段结构、有限样本、汇总和有上限的异常片段。完整数据由专用工具处理；任务提交工具应返回任务标识，后续可独立查询进度。聊天停止与批处理取消分别定义。

输入文件记录内容指纹、批次及解析规则版本。重试复用或替换该输入已有结果，防止重复累计。文件重复与业务记录重复分别处理：多商品订单、退款和跨文件重复导出，需要业务键与规则共同判断。

对账差异应能回到两侧来源文件、工作表和行号，并显示匹配键、规则版本和差异原因。订单粒度、退款、费用和跨期口径，需用真实业务样本明确。

## XLSX 工具选型的条件

| 候选 | 适合评估的任务 | 关键限制 |
| --- | --- | --- |
| [ExcelJS](https://github.com/exceljs/exceljs#formula-value) | Node 内读写 XLSX、格式化输出、流式处理较多记录 | 能保存公式，但不计算结果；打开时请求 Excel 重算不能替代服务端校验。 |
| [pandas](https://pandas.pydata.org/docs/reference/api/pandas.read_excel.html) | 跨表清洗、匹配、分组和统计 | DataFrame 导入导出不等于原工作簿保真编辑；订单号、SKU、条码等需显式控制类型。 |
| [openpyxl](https://openpyxl.readthedocs.io/en/stable/tutorial.html#loading-from-a-file) | 编辑已有工作簿的单元格、公式和样式 | 不计算公式；读取缓存值可能得到旧结果；部分复杂对象不能完整保留。 |

工具选型取决于数据量、模板、公式与格式要求。需要保留公式或复杂模板时，应使用代表性工作簿验证往返保存与结果计算，再确定覆盖范围。

## 下一轮需要明确的条件

1. 现有 Python 脚本的命令行或函数入口、依赖、合并及校验规则。
2. 代表性输入与现有输出，用于确认字段映射、业务键与结果一致性。
3. 生产部署的服务器、成员登录方式与峰值批次并发。

开发验证先本机运行，第一期输入为网页选择文件夹，输出为统一 XLSX 与异常明细。现有程序的 40 分钟耗时作为基准；优化目标在相同输入、明确硬件及计时范围下确定。

第一期方案见 [订单合并 MVP 规格草案](order-merge-mvp.md)。后续规格需覆盖 ERP 与平台对账、销售和库存分析。
