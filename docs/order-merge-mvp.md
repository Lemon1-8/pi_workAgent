# 电商订单合并 Work Agent 规格草案

第一期在本机开发与验证公司内部网页应用，先完成多店铺订单合并。Pi SDK 提供自然语言任务入口与工具调度；独立 Python 执行器处理批量数据。已有 Python 脚本目前不在本机，其具体接口和业务规则待接入检查。

## 使用场景与容量基准

约 50 名员工处理约 200 个店铺的数据。一次任务包含上千份 XLSX，每份约 5MB；按 1,000 份粗估，上传文件总量约 5GB。现有 Python 程序处理一批约 40 分钟。上传、解析、计算和导出应分别计时，端到端耗时与纯计算耗时分开呈现。

来源包括国内电商平台、Temu、旺店通和金蝶。同类数据的字段名称与工作表结构基本一致，但不同来源模板有差异。第一期生成统一结果表，不要求原工作簿的公式与格式保真。

## 员工操作流程

1. 创建订单合并任务，通过网页选择文件夹。
2. 应用展示发现的文件数量与总大小，员工确认本批数据范围后上传。
3. 显示模板识别与字段映射。已确认的同类模板复用规则，未知结构展示差异并等待处理选择。
4. 员工用自然语言描述需求，或直接启动已配置的订单合并流程。两种入口调用同一个任务工具。
5. 查看真实的上传、排队、解析、合并、校验和导出状态。关闭网页后，服务器侧已接收的任务继续执行；重新打开后可查任务状态。本机开发时，这取决于后台进程仍在运行。
6. 查看结果摘要、异常文件与记录，预览结果并下载 XLSX。失败文件可独立重试，结果汇总应避免重复计入。

## 页面与交付物

工作区包含任务列表、任务对话与运行记录、文件及成果面板。任务详情显示本批输入数量、已上传数量、处理成功与失败数量、输出记录数及异常说明。后台没有提供精确进度时，页面显示运行阶段和已知数量。

| 交付物 | 内容 |
| --- | --- |
| 统一订单 XLSX | 使用确认过的字段映射输出订单记录，保留来源标识与必要的业务字段 |
| 异常明细 | 未识别模板、读取失败、缺少字段、非法类型等；标明来源文件、工作表、行号及原因 |
| 批次摘要 | 输入与输出数量、失败或排除项、实际规则版本、耗时和结果文件列表 |

源文件数量、文件名和业务记录数量分别统计。文件内容相同与订单业务重复分别判断，不能仅凭文件名或订单号统一去重。具体订单粒度与去重规则以原脚本和业务样本为准。

Excel 每个工作表最多 1,048,576 行，明细超限时拆工作表或拆文件，批次摘要列出全部输出。[Microsoft 规格与限制](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)

## 候选实现架构

| 部分 | 候选方式 | 责任 |
| --- | --- | --- |
| 网页 | 当前原型采用 HTML、CSS 与 JavaScript | 文件夹选择、上传、任务对话、进度、成果下载 |
| 应用服务 | Node.js 与 JavaScript ESM | 文件接收、持久任务状态、Pi SDK 接入、工具入口和任务事件 |
| Agent | `@earendil-works/pi-coding-agent` 1.2.0 | 理解需求、提出规则、调度任务工具和解释结果 |
| 数据执行器 | Python，优先适配现有脚本 | 按规则解析、规范化、合并、校验和导出 |
| 任务与文件存储 | 本机开发使用持久存储，生产部署按容量确定 | 输入清单、任务状态、逐文件处理结果、原文件和导出成果 |

应用服务与执行器分进程运行。长任务应有自己的持久状态和任务标识，聊天会话与批处理任务分别管理生命周期。任务工具快速返回标识，再独立获取进度与结果。

Pi 只获得完成判断所需的字段结构、有限样本、统计和异常片段。整批原始表格由数据工具读取处理。工具只操作所属任务的文件与结果，成员身份和任务归属在应用层执行。[Pi SDK](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/sdk.md)、[官方执行权限边界](https://github.com/earendil-works/pi/blob/v1.2.0/README.md#permissions--containerization)

## 文件与任务处理要求

上传清单记录相对文件路径、大小、上传状态和服务端文件标识。服务端按受控标识存储，原始名称用于展示与溯源。上传并发与解析并发分别控制；5GB 级批次采用分片或可恢复的逐文件传输，避免一次将整个批次放入内存。

任务至少区分上传中、待确认、排队、运行、完成、失败、取消和中断状态。输入文件记录处理状态、内容指纹及规则版本；重试替换或复用该文件已有结果。任务完成前核对实际输入清单、成功与失败数量、输出记录数。存在无法解释的缺失时，应展示阻断原因，员工选择处理方式后继续。

复用原脚本前，需要确认它是否接受输入清单与输出目录、是否能报告阶段或文件进度、是否支持局部重试。如果脚本当前只能整批运行，先呈现真实状态，再决定为其增加检查点的改造范围。

如需重建解析，评估逐个读取 XLSX、规范化后分批落盘，再用 DuckDB 处理合并和统计。openpyxl 的只读模式可延迟逐行读取；DuckDB 的部分运算可将中间结果写到磁盘，两者都需要结合实际输入测量资源消耗。[openpyxl 优化模式](https://openpyxl.readthedocs.io/en/stable/optimized.html)、[DuckDB 工作负载指南](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)

## 第一条原型的验收标准

| 项目 | 验收方法 |
| --- | --- |
| 文件接收 | 所选输入与服务端清单对应；中断或失败项可定位，不将未上传文件计为已处理 |
| 合并规则 | 以代表性真实样本及现有输出对比字段、记录数量、关键标识和业务校验结果；差异逐项解释 |
| 类型保护 | 检查订单号、SKU、条码的前导零和长数字，日期、金额及缺失值按确认规则处理 |
| 可追溯 | 从输出或异常记录定位原文件、工作表和行号 |
| 可恢复 | 重试同一输入不会重复增加结果；后台重启后恢复真实任务状态，不显示虚假的完成状态 |
| 文件交付 | 所有成果可打开；超限拆分后总记录数正确，完整成果清单可查 |
| Pi 接入 | 使用实际配置的模型，通过同一工具入口发起并查询任务；直接启动流程也能独立工作 |
| 性能 | 在同一批真实文件及明确硬件条件下，分别记录上传、解析、合并、校验和导出耗时，与现有程序对比 |

现有程序的 40 分钟是基准。新系统的性能目标与同时运行批次数，在样本及硬件测试后确定。

## 当前原型的验证状态

阶段 1 已实现。阶段 2 已接入真实 Pi 1.2.0 SDK，并通过离线契约验证；真实模型调用待配置供应商、模型与密钥。阶段 3 的默认适配器已支持清单移除、带原因排除及版本替换，逐文件检查、手动字段映射、工作表选择、模板版本保存与复用，异常集中展示和成功解析检查点的局部复用。成果在交付前核对可读性、字段与记录数，支持分页预览。原业务脚本的订单粒度、去重、退款和费用规则尚待接入。

浏览器验证使用两份真实格式的测试 XLSX，从选择文件夹、上传、内容核对到执行与下载，输出 3 条记录。导出检查确认前导零、20 位字符串订单号与来源字段正确。千文件约 5GB 的吞吐、原程序结果一致性和 50 人部署仍需后续验收。

订单合并验证后，沿用任务、文件和来源追溯能力，增加 ERP 与平台对账、销售及库存分析工具。第一期的字段和批次模型应为这些已确认需求保留来源信息，具体业务规则在对应流程中确定。
